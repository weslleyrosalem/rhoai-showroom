    AHEAD-LLMD: Aurora Supply inference workshop¶

    Aurora's procurement assistant repeats inventory and approval context across requests. Observe how a single GPU, explicit per-request round-robin, and the installed llm-d scheduler serve that workload. Decide from the evidence whether another experiment is justified.

    This is an administrator-led adaptation of the llm-d workshop. ahead-llmd contains workshop materials and sanitized results. The model remains in ai-showroom: two Qwen3 4B replicas on two L40S nodes. No model/GPU deployment is copied, no shared resources are restarted, and no capacity is added. The original Llama/MaaS demonstrations continue independently.

    Activity 1: Identify the inference path¶

    oc whoami
oc whoami --show-server
oc get namespace ahead-llmd
oc get llminferenceservice aurora-qwen-4b -n ai-showroom
oc get pods -n ai-showroom -l app.kubernetes.io/name=aurora-qwen-4b,kserve.io/component=workload -o wide
oc get deployment aurora-qwen-4b-kserve-router-scheduler -n ai-showroom -o yaml

    Expected: two Ready model pods on distinct nodes, prefix-cache-scorer in the scheduler configuration. Inspect the actual images and model revision. The scheduler also uses queue, KV utilization, and no-hit LRU scoring. Prefix scoring being configured does not prove a latency improvement.

    Activity 2: Prepare GuideLLM on the administrator workstation¶

    Python 3.12 and an authenticated oc are required. Use a new local directory outside a public Git checkout for reports; raw GuideLLM reports include local filesystem paths. The script never gives the OpenShift token to GuideLLM or writes it to reports.

    git clone https://github.com/weslleyrosalem/rhoai-showroom.git
cd rhoai-showroom/scripts/ahead-llmd
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python prepare_tokenizer.py tokenizer

    The tokenizer download is pinned to the serving model revision and SHA256-verified. No model weights are downloaded to the workstation. On macOS, the runner selects multiprocessing spawn to avoid a GuideLLM fork startup hang observed during the initial rehearsal.

    Set SHOWROOM_SERVER and SHOWROOM_USER to the independently verified cluster and authorized administrator identity. Set SHOWROOM_PRIVATE_RESULTS to a new absolute directory outside the public repository. The program refuses an identity or server mismatch; never populate its expected identity from the current context in the same command.

    .venv/bin/python ahead_llmd.py \
  --expected-server "$SHOWROOM_SERVER" \
  --expected-user "$SHOWROOM_USER" \
  --guidellm .venv/bin/guidellm \
  --tokenizer tokenizer \
  --output "$SHOWROOM_PRIVATE_RESULTS" \
  --seconds 30

    Add --check-only first to validate identity, model revision, tokenizer checksums, GuideLLM version, and two Ready L40S backends on distinct nodes without inference or port-forwards.

    This runs single-backend observation at concurrency one, then per-request round-robin and llm-d at concurrency two. Every mode is bounded by 30 seconds or 30 requests, whichever occurs first, and requests at most 32 output tokens. All forwards and the loopback broker close on completion or failure. This is a short functional rehearsal, not a saturation or capacity benchmark.

    To produce the sanitized report used by the guide:

    .venv/bin/python summarize_ahead_llmd.py "$SHOWROOM_PRIVATE_RESULTS" /private/review/results-summary.json

    Activity 3: Read the two-backend baseline¶

    Open the round-robin/benchmarks.json or CSV generated by GuideLLM (inspect the actual filenames). Verify successful, errored, and cancelled request counts before reading percentiles. Compare the explicit broker assignment counts and the per-backend success counters in evidence.json; other live traffic can contribute to those counters.

    Activity 4: Read the llm-d path¶

    Read llmd/benchmarks.json and evidence.json. Verify native authentication (anonymous 401, administrator 200), EPP request-counter increase, completed inference requests, backend counters, and prefix cache hits/queries. Treat any delta that includes concurrent traffic as an observation, not exclusively attributable to this client.

    For native dashboards, use OpenShift AI Observe and monitor → Dashboard and the existing model-serving and NVIDIA GPU views. Select the actual Qwen model and the time range of the run. The benchmark client is local, so serving metrics belong to ai-showroom, not ahead-llmd.

    Interpret the results¶

    • The two comparison modes use the same two model replicas, generation settings, dataset shape, and concurrency. Fresh prefix salts differ across modes to reduce prior-run cache reuse; their exact hashes are recorded.
    • Round-robin is explicit per request. A Kubernetes ClusterIP alone does not guarantee per-request round-robin because persistent connections can remain on one backend.
    • The llm-d path includes Gateway authentication and scheduling; the raw baseline uses administrator port-forwards directly to backend pods. These are different end-to-end paths. A latency difference cannot isolate the effect of prefix scoring.
    • Shared live traffic, short samples, warm engines, and no cache reset prevent statistically robust tail-latency or general throughput conclusions. A P95 is a sample statistic, not a guaranteed service level.
    • Local prefix reuse is not cross-node KV transfer or disaggregated prefill/decode. Four-GPU Llama results and the original workshop's 98% example were not reproduced here.

    There is no persistent inference proxy, new cross-namespace service account, or public model route. Rehearsal access requires the existing authorized administrator identity. Keep this privileged path distinct from the customer/native Playground experience.

    Observed rehearsal: September 22, 2026, 06:10–06:11 UTC¶

    All three modes completed 16/16 requests, with zero reported errors or incomplete requests. Native gateway authentication returned anonymous 401 and authorized 200. The two model replicas stayed Ready, their model resource UID/spec remained unchanged, and neither model pod restarted.

    Path Requests P95 TTFT Prefix-hit fraction
    Single backend 16/16 1625.05 ms 92.93%
    Explicit round-robin 16/16 439.27 ms 86.14%
    Native llm-d gateway 16/16 251.36 ms 92.46%

    Concurrency was one for the single-backend observation and two for each two-backend path. Counter changes show where requests went:

    Path Backend 0 Backend 1 EPP requests
    Single backend +16 0 0
    Explicit round-robin +8 +8 0
    Native llm-d gateway 0 +16 +16

    The llm-d sample routed all 16 requests to one backend and observed more prefix reuse than round-robin. That is consistent with prefix affinity at this light load, but other scoring plugins also participate. It does not establish which scorer caused each decision. The observed smaller TTFT is not a causal or general speedup claim.

    The finite 16-row dataset was exhausted. GuideLLM reports a 30-second measurement window, including idle time. Its average 0.533 requests/second here is not the capacity of either path. Mean prompt sizes were 594, 599, and 597 tokens respectively because fresh salts tokenize differently; output size was 32 tokens in every request. These limitations stay with the numbers.

    The sanitized result includes model/runtime/scheduler versions, scoring config, hashes of original reports and prompts, exact timestamps, counts, and limitations. Original CSV/JSON and console logs stay in the private result directory.

    Read the sanitized measured result alongside these limits. This workshop complements the same-GPU engine comparison and the 8:00 a.m. presentation; it answers a different question.
